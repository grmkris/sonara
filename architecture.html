Sonara — Architecture

A browser-based realtime AI music visualizer. Audio goes in; ~15 features stream out at 60 Hz; a thin server orchestrates prompts and generation triggers; fal.ai returns keyframes; a WebGL2 displacement shader carries 60 fps continuity between them.

Reflects code state after the γ scene-collapse + image-anchor work · single-prompt model · three generation paths

00Mental model in one breath

The whole thing in one sentence The browser does the rendering and audio analysis; the server is a thin orchestrator that turns prompt + audio + image-anchor into fal.ai calls and emits events back; Postgres only stores auth + credits. Everything else is in-memory, one object per WebSocket connection.
browser

Audio analysis (Meyda + Web Audio), the zustand store, and the 900-line WebGL2 displacement shader. The visuals never stop moving — the shader is audio-reactive every frame even when no new image arrives.

bun server

One Session per WebSocket. Holds scene state, timers, the credit gate, and the trigger logic. Calls fal.ai. Streams events back. No browser-facing HTTP beyond /health.

external

fal.ai (image gen + the LLM), AudD (song fingerprint), Apple Music (track metadata), Dodo (payments). Each fails silently or degrades — none can take the app down.

One git repo (Turborepo + Bun workspaces). Two deployable apps, four shared packages. Two Docker images, three Railway services.

The split that matters The cut between web and server is by transport + auth model, not "frontend vs backend". Both run server-side business logic, both touch Postgres. The browser hits web over HTTPS with a cookie (auth, payments, uploads); it hits server over WSS with an HMAC ticket (the live session). That's why they can live on different origins with no CORS.

03The scene model recently reshaped

The scene state is the heart of the contract. It used to carry eight separate text fields (subject / action / environment / style / lighting / palette / camera / mood), each with its own UI input. New users saw eight blank boxes and bounced. It was collapsed to a single prompt string — the user types one sentence — while the engine's depth was preserved server-side.

What the user controls now

  • prompt: string — one sentence, e.g. "a snow leopard in falling snow, hushed, slate and pearl"
  • imageAnchor?: { url, strength } — optional uploaded reference image new
  • 5 numeric "treatment" knobs: softness, surrealness, abstraction, stability, intensity

What the server adds

  • version — bumped per keyframe
  • nowPlaying? — set by the song-recognition pipeline
  • The rich ResolvedSceneCore — subjects, hex palette, camera, composition, drift candidates — derived by an LLM from the one sentence (next section)
Why "collapse the surface, keep the engine" The single prompt is purely the input surface. Server-side, an LLM expander parses that sentence back into the same rich structured representation the 8 fields used to provide — so the visual quality and the sumi-e house style survive. The user just doesn't have to author eight fields by hand. The 5 numeric knobs stay because they modulate composition and treatment, which a prompt sentence can't easily express.

04Generation: three paths, one event shape

Every keyframe is produced by exactly one of three paths. They all emit the same frame.preview / frame.final / job.status events, so the client crossfade is identical regardless of which fired.

path 1 · text

Text-to-image

The default. fal-ai/flux-2/klein/9b at 768². ~3–4 s/frame, 1 credit. Prompt is the LLM-expanded scene. No reference image — continuity comes from the client shader.

path 2 · anchor

Image-anchor

When the user uploaded an image. fal-pro/v1.1-ultra with image_prompt_strength from a 3-preset picker (style 0.3 / style+subject 0.55 / lock 0.8). Heavier model — 8 credits, safety checker on.

path 3 · demo

Demo library

Pre-generated WebPs shipped in the Next build, organised into themed decks. Zero credits, zero latency, no fal call. Used for the public demo + anon visitors.

05The trigger decision tree

Session.trigger(source) is the single decision point. The first matching branch wins — order is deliberate. source is one of pause · semantic · periodic · section · voice, collapsed downstream to kind: "auto" | "user" for cooldown logic.

# Session.trigger(source) — first match wins if demoMode && demoDeck → triggerLibrary() # path 3, no credit, no fal if scene.imageAnchor → triggerAnchor() # path 2, 8 credits, flux-pro if userId == null → bail # anon never reaches paid fal if !scene.prompt.trim() → skip # nothing to generate else → streamPreview() # path 1, 1 credit, klein/9b

What fires a trigger:

SourceFired bykind
semanticPrompt edit whose semantic-diff clears the 0.4 thresholduser
voiceDictated prompt — lowers the threshold to 0.1 so small tweaks still fireuser
pauseA deliberate edit settling (debounced)user
sectionAudio energy delta crosses a section boundary (chorus/drop)auto
periodicTimer; cadence scales with intensity (8–16 s)auto
A subtle but important fix User-initiated triggers now await the LLM expansion before calling fal. Previously the first frame after a prompt edit used a bland deterministic fallback while the LLM filled the cache for the next frame — so you'd type, get a flat frame, then ~12 s later a much nicer one. Awaiting on user triggers (but not auto-triggers, which shouldn't block) makes the first frame land rich. Costs ~1–2 s of latency for a large quality jump.

06The LLM expander & its cache

This is the bridge between "one user sentence" and "rich structured prompt". scene-llm-expander.ts sends the prompt + 5 knobs to fal's any-llm (Gemini) and gets back a ResolvedSceneCore: a scene title, a subjects array (subject[0] is the byte-stable identity anchor), hex palette, lighting, mood, composition, camera, and 6–10 atmospheric "drift candidates".

trigger()
Needs a resolved scene to build the fal prompt
resolver
Hashes the prompt. Cache hit → return instantly. The 5 knobs do not bust the cache.
resolver
Cache miss, auto-trigger → return deterministic fallback immediately, kick off the LLM call in the background to warm the cache
resolver
Cache miss, user-trigger → await the LLM call so the first frame is rich (the fix above)
fal any-llm
Returns structured JSON; validated by zod; cached by prompt hash (5-min TTL)
prompt-compiler
Serializes ResolvedSceneCore → the final FLUX prompt string
Why cache by prompt One LLM call per unique prompt. Same prompt → same JSON → same character across every keyframe for that prompt. The cache is what gives the visuals consistency across the rapid auto-triggers without re-paying for the LLM each frame. In-memory only; warms naturally after a deploy.

07Drift & visual continuity

Two mechanisms keep a fast-moving session from feeling random:

Drift trajectory (server)

prompt-drift.ts pre-samples a 10-slot trajectory of atmospheric micro-modifiers ("ink wash", "dappled light"), biased by session progress (intro → build → dissolve arc). One is appended per keyframe. Seeded from the LLM's drift_candidates when available, else a curated static pool.

Displacement shader (client)

The real continuity. A monolithic WebGL2 fragment shader (~750 lines GLSL, ~30 audio-reactive uniforms) ping-pongs feedback FBOs and crossfades between keyframes over 800 ms. It runs at 60 fps regardless of how often new images arrive — so the visual feels alive even between generations.

10Hot flow — voice dictation reworked

Voice used to be field-keyed push-to-talk (hold S/E/M/P to speak into one of the four fields). With one prompt field, it's now tap-to-dictate: tap the mic, the interim transcript streams into the textarea as a draft, tap to stop, review, press Enter. There is no LLM "intent parsing" — dictation is just typing with your voice.

User
Taps the mic button on the textarea

Browser SpeechRecognition in continuous mode; onResult streams interim text → fills the textarea draft
User
Taps mic to stop, edits if needed, presses Enter
PromptInput
Commits via voice.patch → server uses the lower 0.1 semantic threshold so even small spoken tweaks regenerate

13Credits & the money path

fal.ai dominates cost by two orders of magnitude, so the credit system exists almost entirely to bound it.

The gate (per frame)

  • Try to debit the per-frame cost (1 text / 8 anchor) atomically from the balance
  • Balance empty → try a free-tier slot (3 / hour)
  • Neither → deny with a cooldown-aware error toast
  • fal call fails after debit → refund in the same ledger

Top-up path

  • User buys a credit pack via Dodo Payments checkout (server-side create on web)
  • Dodo webhook → web → writes a kind:'topup' ledger row
  • Balance is the sum of the ledger; race-safe atomic SQL on debit
  • Demo + anon paths never touch credits at all
Where the money logic actually runs Credit debit happens on the server (per frame, raw pg queries, no Drizzle). Credit top-up confirmation happens on web (the Dodo webhook + oRPC confirmTopUp). Both write to the same ledger table. Pricing lives in packages/shared/src/pricing.ts as the single source of truth.

The HMAC ticket trick The WebSocket is the only path that uses a ticket instead of a cookie. The browser RPC-calls mintWsTicket() (cookie-authed, same-origin via the gateway), gets a short-TTL signed ticket (carrying userId or null for anon), and passes it as a query param on WS upgrade. The server verifies the HMAC. The WS is now same-origin (wss://sonara.fm/ws, gateway → server); the ticket scheme is kept because it cleanly carries identity to the upgrade without parsing cookies at the socket layer.

(2) The local .env DATABASE_URL points at a localhost Docker Postgres for dev only; prod injects Railway's ${{Postgres.DATABASE_URL}} at runtime. Never infer the prod stack from .env.
